# Architecture

SkinShift is a Manifest V3 extension with no build step. Every file is a readable classic script.
This document covers the pieces, how they talk to each other, and why they are built this way.
Plan deviations are recorded in [DECISIONS.md](../DECISIONS.md).

## Layout

```
manifest.json                       MV3 manifest; scoped host permissions
src/
  background/service-worker.js      IndexedDB owner; relays wallpaper bytes; sets toolbar badge
  content/
    content-script.js               entrypoint: picks adapter, waits for surface, reconciles state
    overlay-manager.js              owns the single background layer, MutationObserver, theme
    site-adapters/*.js              one file per site: ordered selector fallbacks
  lib/
    constants.js                    namespace, storage defaults, presets, limits, settings repair
    idb-wrapper.js                  ~80-line IndexedDB helper (vendored, no CDN)
    contrast.js                     WCAG maths and worst-case verdict (pure, testable in Node)
    image-utils.js                  validate → decode → resize → JPEG → column-average sample
  popup/                            settings UI: presets, sliders, upload, readability, sites
  styles/overlay-base.css           static layer CSS, injected before any script runs
icons/                              original artwork, generated by tools/make-icons.py
test/                               unit (node --test) and e2e (Playwright, real Chromium)
```

Scripts load in one fixed order. The content scripts are listed in `manifest.json`; the popup
loads them in `popup.html`. `constants.js` always comes first, because it creates `self.SkinShift`.

## The adapter pattern

An adapter is a plain object pushed onto `SkinShift.adapters`:

```js
{
  id: 'claude',
  name: 'Claude',
  hosts: ['claude.ai'],
  surfaces:    ['main', '[role="main"]', ...],   // ordered fallbacks; first match = "supported"
  transparent: ['main', '#root', ...]            // opaque containers to clear
}
```

- **`surfaces`** answers one question: is the chat UI mounted? The first selector that matches
  wins. Zero matches after 10 seconds means the site is `unsupported`. The extension stays inert
  and the popup says so. The page is never touched.
- **`transparent`** is the set of site containers whose opaque backgrounds are cleared, so the
  wallpaper shows through. It is applied as one selector-based `<style>` rule. Invalid selectors
  are filtered out one by one, so a single bad entry cannot disable the whole rule.

The adapter is the only file that knows anything about a site. Adding a site means adding a file
and a host permission, not changing the engine.

## Overlay strategy

```
<body>
  <div id="skinshift-root">        position:fixed; inset:0; z-index:-1; pointer-events:none
    <img class="ss-wallpaper">     the user's photo, object-fit: cover
    <div class="ss-scrim">         rgba(theme tint, opacity) + backdrop-filter: blur()
  </div>
  <div id="__next"> … the site's own UI, with its opaque surfaces made transparent … </div>
</body>
```

**Why body level, z-index -1.** React-style frameworks replace the nodes they own. A layer
injected inside the chat tree is wiped on the next render. A sibling of the app root survives most
renders. The MutationObserver re-inserts it if the host removes it.

**Why transparency is a stylesheet.** A selector keeps applying to nodes created after injection.
Inline styles would be lost on the next render.

**Why the tint follows the site's theme.** The site's own dark toggle changes the text colour.
The scrim colour is chosen to match, and a `MutationObserver` on `<html>`/`<body>` attributes
re-checks the theme on change. The overlay sits underneath the site's own UI and never fights it.

**Why blur is a separate, optional path.** `backdrop-filter` is the expensive part. Performance
mode drops it and keeps the tint, which also keeps readability.

**Why the wallpaper is an `<img>`.** A CSS background fails silently when a page CSP blocks
it. An `<img>` reports the failure through its own `error` event, and the handler hides the image
while the scrim keeps the chat readable. See D-010 for the test evidence.

## Storage design

| Data | Where | Why |
|---|---|---|
| Settings (preset, opacity, blur, perf mode, site toggles, `hasWallpaper`, `sample`, version timestamp) | `chrome.storage.local` | small, synchronous-feeling, emits `onChanged` to every tab |
| Wallpaper Blob | IndexedDB, extension origin, key `current` | blobs don't belong in storage; survives restarts |
| Object URL | memory, one page instance | URLs die on reload; regenerated from the Blob each time |

Content scripts run in the **host page's** origin, so they cannot read the extension's IndexedDB.
The service worker reads the Blob and returns it as base64 over `chrome.runtime` messaging. The
content script decodes it locally. No network is involved.

`wallpaperUpdatedAt` is written to storage and IndexedDB with the same timestamp. A version
mismatch is how a tab knows it must reload the image, so a half-finished upload can never leave
the two stores disagreeing.

`normalizeSettings` runs on every read. Missing or malformed fields fall back to defaults, so
corrupt storage cannot break the extension.

## Upload pipeline

1. **Validate.** Reject over 15 MB before decoding. Accept only JPEG, PNG and WebP. SVG is
   refused because it can carry script.
2. **Decode** with `createImageBitmap`.
3. **Fit** into 1920×1080 with contain-fit. Never upscale, never crop.
4. **Flatten and encode.** Fill white under the image, then encode JPEG at 0.8. This removes
   alpha and metadata.
5. **Sample** the central 60% of the width at 64 px wide, to get one average colour for the
   readability verdict.

## Readability verdict

The overlay composites a tint over the wallpaper. Alpha compositing is linear per channel, so the
average of the composite equals the composite of the averages. The verdict therefore needs only
the stored average colour, plus the opacity. It evaluates both the light and dark theme, and
reports the worse of the two. See D-012.

## Failure modes and where they are handled

| Failure | Handling |
|---|---|
| Selector drift | adapter fallbacks; unsupported status; selector-check spec |
| SPA re-render removes overlay | throttled MutationObserver re-inserts root |
| Storage limits | blob in IndexedDB; unlimitedStorage; upload resize |
| Readability | live verdict; presets verified at the extremes; toolbar warning |
| CSP / Trusted Types | no string-to-DOM sinks; `<img>` error fallback; strict-CSP test |
| Light/dark conflicts | underneath the site; theme observer |
| Performance | perf mode drops backdrop-filter |
| Object URL lifecycle | never persisted; regenerated per page init |
| Extension reloaded under a live tab | messaging wrapped; orphaned tab goes quiet |

## Testing layers

- **Unit** (`test/contrast.test.js`): WCAG maths, preset guarantees, settings repair.
- **E2E, mock pages** (`test/e2e/*.mjs`): real Chromium with the unpacked extension and
  `context.route()` mocks. Covers the lifecycle, multi-site behaviour, strict CSP and the popup.
- **Live selector check** (`test/selector-check.spec.js`): headed, against real sites, with a
  logged-in profile. This is the only test of the real DOM and is the one to run before each release.

## Tradeoffs considered

- **Bundler vs. none.** None. The code is small and auditable, and the store reviewer or a
  contributor can read every line.
- **Single background layer vs. per-element.** Single. One node is cheaper to keep alive.
- **Average vs. per-pixel readability.** Average. Exact for opacity, free to recompute.
  Per-pixel is a v0.2 candidate.
- **Popup-only warning vs. in-page banner.** Popup plus toolbar badge. An in-page banner would
  add a DOM node to someone else's page for a cosmetic warning.
